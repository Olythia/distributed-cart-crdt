# 基于 CRDT 的分布式购物车系统

一个基于 **Flask + SQLite + Docker Compose**
构建的多节点分布式购物车实验系统。系统采用 **OR-Set（Observed-Remove
Set）** 管理购物车商品，使用版本向量记录节点更新进度，并通过数据复制与
CRDT 合并机制处理网络分区、消息异常、节点故障和并发请求。

> 本仓库主要用于课程项目与分布式系统实验，包含基础功能验证、故障注入测试及性能测试。实验结果为本项目当前实现与测试环境下的观测结果，不代表对所有故障组合或生产环境的完整保证。

## 项目背景

在多设备购物场景中，用户可能同时通过手机、电脑等设备访问不同服务节点。网络分区期间，各节点可能无法及时交换更新。如果采用简单的覆盖式更新，恢复同步时可能丢失某个节点独立产生的商品修改。

本项目实现一个多副本购物车系统，重点验证：

1.  网络分区期间，节点能否继续处理本地购物车请求；
2.  网络恢复后，不同节点的并发更新能否正确合并；
3.  节点宕机、消息重复、延迟、乱序和请求重试等异常情况下，数据能否保持可靠；
4.  并发更新与热点访问场景下，系统能否进行基本控制与性能优化。

## 系统功能

-   多节点独立运行，各节点保存本地购物车状态。
-   基于 OR-Set 管理商品添加与删除。
-   使用版本向量记录各节点逻辑更新进度。
-   节点间通过复制机制交换数据，并使用 CRDT 规则合并。
-   使用 SQLite 持久化节点状态与相关元数据。
-   支持网络分区期间本地读写，网络恢复后进行数据同步。
-   支持基于版本的 CAS 并发更新控制。
-   使用 `request_id` 对重复业务请求进行去重处理。
-   提供故障注入与实验脚本，覆盖九类故障场景。
-   对热点 Key 进行缓存和客户端多节点轮询性能测试。

## 系统架构

系统包含四个节点：

  节点   容器名称        主机访问端口
  ------ ------------- --------------
  A      `kv-node-a`             8001
  B      `kv-node-b`             8002
  C      `kv-node-c`             8003
  D      `kv-node-d`             8004

每个节点运行独立服务并维护自己的 SQLite
数据库。节点通过复制机制交换状态，接收端根据 CRDT
合并规则整合更新。容器数据目录通过 Docker
数据卷映射到主机，以支持节点重启后的数据恢复。

简化的数据流：

``` text
客户端请求
    |
    v
节点 A / B / C / D
    |
    +---- 本地购物车操作 ----> OR-Set 状态
    |                           |
    +---- 版本向量更新 ----------+
    |
    +---- SQLite 持久化
    |
    +---- 节点间数据复制
                |
                v
        CRDT 合并与最终收敛
```

## 核心机制

### OR-Set

购物车采用 OR-Set
思想。每次添加商品都会生成独立的唯一标记（add-tag）。商品数量由当前有效标记数量决定，而不是直接对不同副本的商品数量进行简单累加。

删除操作只删除当前操作所观察到的添加标记。因此，在删除与并发添加发生于不同节点时，未被删除操作观察到的新添加标记可以在合并后保留。

OR-Set
合并具有幂等性：同一标记被重复合并不会被当作新的添加操作，从而避免复制消息重复导致商品数量重复增加。

### 版本向量

版本向量记录各节点的逻辑更新计数，例如：

``` json
{
  "A": 3,
  "B": 2,
  "C": 1
}
```

版本向量用于比较节点所记录的更新进度。版本向量相同表示记录的更新进度一致；判断购物车是否一致时，还应同时检查实际购物车内容。

### 数据持久化

节点使用 SQLite 保存购物车状态和相关版本信息，并通过 Docker
数据卷保留容器数据。SQLite WAL（Write-Ahead
Logging）模式用于支持数据库事务与日志恢复机制。

### CAS 并发控制

CAS（Compare-And-Swap）根据客户端期望版本与当前版本是否匹配来决定是否执行更新。项目通过锁保护版本检查与更新过程，避免两个竞争操作都基于同一旧版本成功提交。

### 请求幂等

请求通过 `request_id`
标识。服务器对已处理请求保存响应记录；相同请求标识再次到达时，返回此前保存的结果，避免重复执行商品添加。

### 依赖环境

-   Python（项目使用虚拟环境）
-   Flask
-   SQLite
-   Docker
-   Docker Compose

`requirements.txt`（如存在）或项目实际依赖配置为准。

``` bash
git clone https://github.com/Olythia/distributed-cart-crdt.git
cd distributed-cart-crdt
```

Windows PowerShell：

``` powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
```

``` powershell
pip install -r requirements.txt
```

### 使用 Docker Compose 启动

在包含 `docker-compose.yml` 或 `compose.yaml` 的项目目录中执行：

``` bash
docker compose up -d --build
```

查看节点状态：

``` bash
docker compose ps
```

查看日志：

``` bash
docker compose logs -f
```

停止服务：

``` bash
docker compose down
```

## 接口说明

项目实验中使用了以下接口：

  方法     路径                          作用
  -------- ----------------------------- ----------------------------
  `GET`    `/version`                    查询节点版本向量或版本信息

## 实验与故障测试

实验由基础功能实验和九种故障测试组成。故障测试结果基于本项目实际执行记录。

### 基础实验

  实验         验证内容
  ------------ --------------------------------------
  基础实验 0   四节点启动、接口访问、商品添加与查询
  基础实验 1   正常状态下跨节点数据复制
  基础实验 2   网络分区期间各节点独立添加与查询
  基础实验 3   网络恢复后的 CRDT 数据合并
  基础实验 4   版本向量比较与同步进度检查

### 九种故障测试

  -----------------------------------------------------------------------------------------------------------
  编号                    故障场景                 验证内容与结果概述
  ----------------------- ------------------------ ----------------------------------------------------------
  E1                      副本节点宕机             其他节点继续服务；故障节点恢复后重新同步

  E2                      双向网络分区与消息重复   分区期间独立写入；重复消息不造成重复计数，恢复后数据收敛

  E3                      消息延迟与乱序           延迟和乱序消息经 CRDT 合并后能够完成同步

  E4                      SQLite 持久化与节点重启  重启后恢复购物车数据和版本信息

  E5                      新节点数据迁移中断       中断后重新执行全量迁移；OR-Set 合并避免同一标记重复计数

  E6                      热点 Key 与高并发性能    比较单节点基准与缓存、四节点轮询方案的性能

  E7                      并发 CAS                 20 组竞争测试中，每组一个操作成功、一个操作失败

  E8                      应用层时钟回拨           模拟时间偏移，检查延迟队列与逻辑版本计数

  E9                      写入成功但响应延迟       客户端超时后使用相同 `request_id`
                                                   重试，避免重复写入并验证跨节点同步
  -----------------------------------------------------------------------------------------------------------

### 关键实验说明

-   **E5**：验证的是中断后重新执行全量迁移，并利用 OR-Set
    合并幂等性避免重复计数；不是严格的 checkpoint 或断点续传。
-   **E8**：使用应用程序层时间偏移模拟时钟回拨，并未修改操作系统时间。
-   **E9**：通过服务端延迟响应模拟客户端超时，不等同于真实丢弃 TCP
    响应包。当前实验验证请求记录保存后的重复请求处理；商品状态提交与请求响应记录保存并非任意崩溃情况下都严格同事务原子。
-   **E2/E3**：实验结果说明在所测试的消息重复、延迟与乱序条件下，系统能够正确合并；不应据此推断所有网络故障组合均已覆盖。

## 性能测试

E6 热点 Key 测试采用 1000 次请求、20 个并发线程，热点 Key 占比 50%。

  指标             单节点基准   缓存 + 四节点轮询
  -------------- ------------ -------------------
  请求总数               1000                1000
  成功请求数             1000                1000
  QPS                  519.95              845.94
  平均响应时间      36.962 ms           23.276 ms
  P95               65.498 ms           39.068 ms
  P99               87.596 ms           49.469 ms
  缓存命中率              ---               89.6%

优化方案中 QPS 从 519.95 提升至 845.94，平均响应时间从 36.962 ms 降至
23.276 ms。

> 基准阶段为单节点无缓存，优化阶段同时加入了本地缓存和四节点轮询。因此，该实验说明整体优化方案取得改善，不能单独归因于缓存或多节点分流中的某一个因素。

## 实验结论与限制

实验验证了系统在所设计的故障场景下具备以下能力：

-   网络分区期间节点可使用本地副本继续处理请求；
-   网络恢复后，通过复制与 OR-Set 合并实现最终收敛；
-   重复消息和重复请求在相应机制下不会导致重复计数或重复执行；
-   SQLite 数据卷支持节点重启后的数据恢复；
-   CAS 能够控制同一版本上的竞争更新；
-   缓存与客户端轮询方案改善了本次热点访问测试的性能。

当前系统仍是实验性实现。实验覆盖范围、故障注入方式、持久化事务边界以及性能测试环境均会影响结论。结果不应被解释为已经达到生产级高可用或严格一致性保证。
